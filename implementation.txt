mplementation Plan: Two-Body Orbital Docking Dynamics Simulator
(C++17, OOP, OpenGL 3.3 Core Profile — macOS compatible)
Scope re-interpretation: This plan implements the Dynamics Engine, NGC interface, disturbance model, and visualization/GUI requirements from the SOW (§3.3), but replaces the physical Stewart-Platform/VDE hardware loop with a pure-software two-body simulation: two simple square (planar quad / thin-box) objects, Chaser and Target, orbiting under Newtonian gravity, each with full 6-DOF rigid-body dynamics, rendered in real time. All coordinate-frame, quaternion, and interface conventions are taken verbatim from the SOW so the engine stays faithful to the spec even though the physical rig is gone.

Key design decision — two independent clocks: the SOW specifies Dynamics Engine rate ≤1 ms and visualization refresh 60 Hz. These run at different rates, so the physics loop runs on a fixed-timestep accumulator (optionally on its own thread) and publishes an immutable SimState snapshot that the renderer consumes lock-free (double buffer / atomic pointer swap). This mirrors the SOW's decoupling of Dynamics Engine, Motion Controller and Visualization Software as separate concurrent subsystems.

3. Math & coordinate-frame layer (engine/math/)
This is the foundation everything else depends on, and it must match the SOW's conventions exactly (not just "a" quaternion convention — theirs).
3.1 Quaternion convention (scalar-last, matches SOW eq. in §3.3.1)
// engine/math/Quaternion.hpp
class Quaternion {
public:
    // Storage order matches SOW: q = [q1, q2, q3, q4], q4 = scalar (cos(alpha/2))
    double q1, q2, q3, q4;

    static Quaternion FromAxisAngle(const Vec3& axis, double angleRad);
    static Quaternion FromDCM(const Mat3& A);      // 4-branch robust extraction (SOW gives all 4 forms)
    Mat3   ToDCM() const;                          // exact matrix from SOW: B[Aq]I
    Quaternion operator*(const Quaternion& rhs) const; // Hamilton product, scalar-last convention
    Quaternion Normalized() const;
    Quaternion Conjugate() const;
    Vec3 Rotate(const Vec3& v) const;               // v_rotated = q * v * q^-1
    Quaternion Derivative(const Vec3& omega_body) const; // q̇ = 0.5 * Ω(ω) * q
};

FromDCM implements all four branches given in the SOW (choosing the numerically most stable one based on max(a11,a22,a33,trace)), verified to produce identical quaternions as the doc notes ("The above presents 4 different solutions, but the resulting quaternions are identical").
Unit tests: round-trip DCM→quat→DCM, compare against the SOW's explicit matrix formula element-by-element.
3.2 DCM / Euler layer (engine/math/Euler.hpp)
Implements the intrinsic Yaw(Z)-Pitch(Y)-Roll(X) sequence exactly as in Figure 6/eq. in §3.3.1: B[A_{ψ,θ,φ}]_I = [Roll]_x2 · [Pitch]_y1 · [Yaw]_z
Mat3 EulerToDCM(double yaw, double pitch, double roll)
EulerAngles DCMToEuler(const Mat3& A)
Explicit unit test hard-codes the 3×3 symbolic matrix from the SOW (cθcψ, cθsφ, -sθ; ...) and checks numeric agreement.
3.3 Reference frames (engine/frames/Frame.hpp)
enum class FrameId { ECI, LVLH_Chaser, LVLH_Target, Body_Chaser, Body_Target, Dock_Chaser, Dock_Target };

class ReferenceFrame {
public:
    FrameId id;
    // Pose of this frame relative to ECI, at a given time:
    virtual Vec3 OriginInECI(const SimState&) const = 0;

};

class DockFrame       : public ReferenceFrame { /* body frame + fixed offset (lever arm) to interface face */ };

public:

This single utility produces every relative pose the SOW's Table 5 requires:
Chaser-dock w.r.t. Target-dock → the 14-element Y vector
Chaser/Target 12-state in ECI → NGC inputs
Chaser body w.r.t. Target LVLH → also required by NGC per §3.3.1

4. Rigid body & dynamics engine (engine/dynamics/)
4.1 RigidBody
class RigidBody {
public:
    // Identity
    std::string name;                 // "Chaser" / "Target"

    // Mass properties (editable at runtime per SOW Table 8 item 7)
    double mass;
    Mat3   inertiaTensorBody;         // about C.G., body axes
    Vec3   cgOffsetFromGeomCenter;    // if square's C.G. isn't its centroid
    Vec3   dockFrameOffsetBody;       // lever arm to docking/interface face

    // State (ECI frame)
    Vec3       positionECI;
    Vec3       velocityECI;
    Quaternion attitude;              // ECI -> Body
    Vec3       angularVelocityBody;   // ω, expressed in body axes

    // Accumulators (reset each physics step)
    Vec3 forceAccumECI;
    Vec3 torqueAccumBody;

    void ClearAccumulators();
    void ApplyForceECI(const Vec3& F);
    void ApplyTorqueBody(const Vec3& T);
    void ApplyForceTorqueBodyFrame(const Vec3& F_body, const Vec3& T_body); // matches SOW F_C/F_T layout

    StateDerivative ComputeDerivative(const ForcesTorques& externalBody) const;
};

StateDerivative bundles (v, a, q̇, ω̇) and is what the integrator consumes — this keeps RigidBody a pure data+derivative class (single responsibility), with all stepping logic living in the integrator.
4.2 Equations of motion
Translational (ECI): m·a = F_gravity + F_disturbance + R_body→ECI · F_NGC_body
Rotational (body axes, Euler's rigid body equation): I·ω̇ = T_ext − ω × (I·ω)
Attitude kinematics: q̇ = 0.5 · Ω(ω) · q (scalar-last form matching SOW quaternion convention)
4.3 Integrator (engine/dynamics/Integrator.hpp)
class IIntegrator {
public:
    virtual void Step(RigidBody& body, const ForcesTorques& ft, double dt) = 0;
    virtual ~IIntegrator() = default;
};

class RK4Integrator : public IIntegrator { /* classic 4-stage RK4 on the 13-element state (r,v,q,ω) */ };

RK4 chosen over Euler for stability at the SOW's ≤1ms step with stiff contact-spring forces during the validation test.
Quaternion is renormalized after every step (standard practice — RK4 doesn't preserve unit norm exactly).
Step size is a configurable constant (kDynamicsEngineDt = 1.0 ms default, matching SOW Table 7 item 4).
4.4 Two-body gravity model (engine/dynamics/Gravity.hpp)
class TwoBodyGravity {
public:
    static Vec3 AccelerationECI(const Vec3& r_ECI, double mu = kEarthMu);
    // a = -mu * r / |r|^3   (Newton's law, per SOW §3.3.1 "Newton's Law of Gravitation, two-body problem")
};

Both Chaser and Target orbit independently under this (they're close together relative to Earth radius, so effectively the same gravity field, exactly as real proximity-ops dynamics work — relative motion emerges from the difference).
4.5 Disturbance models (engine/dynamics/disturbances/) — pluggable, per SOW's 3 named disturbances
class IDisturbanceModel {
public:
    virtual ForcesTorques Compute(const RigidBody& body, const SimState& env) const = 0;
    virtual ~IDisturbanceModel() = default;
};

class AtmosphericDragModel      : public IDisturbanceModel { /* F = -0.5*rho*Cd*A*|v_rel|*v_rel */ };
class GravityGradientTorqueModel: public IDisturbanceModel { /* T = 3*mu/r^3 * (r̂ × I·r̂) */ };
class J2PerturbationModel       : public IDisturbanceModel { /* "higher order gravity models" from SOW */ };

DynamicsEngine holds std::vector<std::unique_ptr<IDisturbanceModel>> per body, so any subset can be enabled/disabled at runtime — directly satisfying the GUI requirement "flag for Disturbance Force/Torques module inclusion/exclusion" (SOW Table 8, item 10).
4.6 No active control — free-drift + gravity + disturbances + contact only
The NGC (Navigation/Guidance/Control) module is explicitly out of scope. Neither the Chaser nor the Target has any active thruster/controller driving it. All motion comes from:
Two-body gravity (§4.4)
Disturbance models, if enabled (§4.5)
The contact-spring force when the two squares' docking faces come within range (§5)
The DynamicsEngine's equations of motion still have a slot for "external body-frame force/torque" (so the architecture doesn't have to be reworked if a controller is ever added later), but it is wired to a trivial always-zero stub rather than any control logic:
struct ExternalForcesTorques {
    Vec3 F_chaser_body{0,0,0}, T_chaser_body{0,0,0};
    Vec3 F_target_body{0,0,0}, T_target_body{0,0,0};
};
// DynamicsEngine::Step() always uses a zero-filled ExternalForcesTorques —
// there is no INGCModule, no controller class, and no GUI "NGC mode" selector.

This removes an entire subsystem from the plan: no engine/ngc/ directory, no NGC-related GUI dropdown, and the "Initialization – NGC mode and failure cases" row from SOW Table 8 is dropped from the GUI (see §6.5 update below).
4.7 DynamicsEngine (composition root for physics)
class DynamicsEngine {
public:
    DynamicsEngine(RigidBody chaser, RigidBody target,
                   std::unique_ptr<IIntegrator> integrator);

    void AddDisturbance(BodySelector who, std::unique_ptr<IDisturbanceModel> model);
    void EnableDisturbances(bool enabled);           // GUI toggle
    void SetDockingRoleAssignment(DockingRoleAssignment);

    void Step(double dt);                            // one fixed-timestep advance
    SimState GetSnapshot() const;                     // thread-safe read for renderer/GUI

private:
    RigidBody m_chaser, m_target;
    ContactSpringModel m_contact;
    std::vector<std::unique_ptr<IDisturbanceModel>> m_chaserDisturbances, m_targetDisturbances;

No INGCModule member, no constructor parameter for it, no runtime mode-switching — the engine's only inputs are the two bodies' initial states, the integrator strategy, and whichever disturbance models get attached.
SimState is the exact snapshot published across the thread boundary: both RigidBody states, the derived Y (14-element relative vector), both 12-element ECI states, current forces/torques for the sidebar, and a timestamp.

6. Visualization layer — OpenGL 3.3 Core, macOS-compatible
6.1 Why these specific choices for Mac compatibility
macOS only supports OpenGL up to 4.1, and only exposes Core Profile contexts (no compatibility profile) — so the SOW's "OpenGL 3.3" target must be requested as 3.3 Core explicitly, with GLFW_OPENGL_FORWARD_COMPAT = GL_TRUE and GLFW_OPENGL_PROFILE = GLFW_OPENGL_CORE_PROFILE set before window creation. This code path also runs unmodified on Windows/Linux.
Use GLFW (windowing/input, cross-platform, trivial Mac support) + GLAD (function loader, generated for GL 3.3 core) — avoid GLUT/legacy loaders.
Avoid any glBegin/glEnd immediate-mode, geometry shaders, or compute shaders (not guaranteed on Mac's capped GL 4.1) — everything via VAOs/VBOs + vertex/fragment shaders only, which is fully 3.3-core-safe.
GLSL version string #version 330 core in every shader.

6.3 Rendering scale — zoomed-in relative-motion view (resolved)
True orbital scale (Earth radius ≈ 6,371 km, orbital altitudes in hundreds/thousands of km) would render the two boxes as sub-pixel dots — completely unreadable. So the primary view uses a relative-motion camera frame, not true ECI scale:
The Camera's orbit pivot (m_target) tracks the midpoint between Chaser and Target in ECI, not the Earth's center.
Positions fed to the renderer are the relative position of each body from that midpoint, scaled to a fixed visual unit (e.g. 1 rendered unit = 1 meter of relative separation) — completely decoupled from the true ECI coordinates used internally by DynamicsEngine. This is purely a render-time transform; the physics never sees or uses this scaling.
A relative-motion trail (m_relativeTrail, already in the Renderer class above) traces the closing/departing path between the two boxes over time — this is the main visual signal for "are we approaching, docking, or drifting apart."
Earth itself is not rendered in this primary view at true scale (it would be a barely-curved backdrop at best, or absent entirely) — the MakeEarthSphere() mesh from §6.2 is repurposed instead for a small secondary/inset view (see below), not the main viewport.
Small ECI/orbit context inset: a second, much smaller viewport (rendered as a separate small glViewport region in the corner of the window, reusing the same Renderer with a different Camera instance) shows the full orbit at true ECI scale — Earth as a sphere, with the Chaser/Target pair rendered as a single bright dot or small marker (too close together to distinguish at that scale) along its orbital path. This answers "where in the orbit are we" without needing the two objects to be individually visible at that zoom level. It uses the same 12-state ECI data the main view already has — no extra computation, just a second draw pass with a different camera and projection.

6.7 Timing-verification logging (proves the physics loop actually runs at the target rate)
Purpose: the SOW requires a specific Dynamics Engine rate (Table 7). It's not enough for the code to intend a 2 ms step — the system must measure and log the real wall-clock time each step actually took, so you can open the CSV afterward and verify the engine held 2 ms rather than assuming it did. This is a separate concern from the physics-results logging in §6.6 (DataLogger) — it's a diagnostics log about the loop itself, not the simulation.
Measurement method: every step, the physics thread takes a std::chrono::steady_clock timestamp immediately before and after calling DynamicsEngine::Step(). steady_clock is used (not system_clock) because it's monotonic and immune to system clock adjustments — the only clock suitable for measuring elapsed durations.
// io/TimingLogger.hpp
struct TimingSample {
    uint64_t stepIndex;
    double   simTimeS;         // stepIndex * dtTarget
    double   wallTimeS;        // steady_clock time since run start
    double   dtTargetMs;       // configured target, e.g. 2.0
    double   dtActualMs;       // measured wall-clock duration of this step
    double   dtErrorMs;        // dtActualMs - dtTargetMs
    double   cumulativeDriftMs;// wallTimeS*1000 - simTimeS*1000
};

class TimingLogger {
public:
    explicit TimingLogger(double dtTargetMs);
    void RecordStep(uint64_t stepIndex, std::chrono::steady_clock::time_point stepStart,
                     std::chrono::steady_clock::time_point stepEnd);   // called from physics thread
    void FlushToCSV(const std::filesystem::path& file) const;         // called from main thread after run
    TimingSummary ComputeSummary() const;                              // mean/stddev/min/max/% in tolerance
private:
    std::vector<TimingSample> m_samples;   // pre-reserved, no per-step heap allocation
    std::chrono::steady_clock::time_point m_runStart;
    double m_dtTargetMs;
};

It also becomes an automated test: a unit/integration test runs N steps and asserts pct_within_tolerance > 99%, catching any future regression (e.g. an accidentally-added allocation or lock inside the hot loop) automatically rather than relying on manual inspection.

class Application {
public:

private:
    void PhysicsThreadLoop();     // fixed dt accumulator, up to real-time or faster-than-real-time
    void RenderLoopTick();        // 60Hz-capped main-thread loop (GL context must stay on main thread on macOS!)

    GLContext                    m_glContext;
    Renderer                    m_renderer;
    Camera                      m_camera;
    DynamicsEngine               m_engine;
    std::atomic<SimState*>        m_latestState;   // lock-free snapshot handoff
    std::thread                  m_physicsThread;
    std::atomic<bool>              m_running;
    DataLogger                   m_logger;
};

Important macOS-specific constraint: all GLFW/OpenGL calls must stay on the main thread (Cocoa requirement) — so the design puts physics on the background thread and keeps rendering + GUI + GLFW event polling on the main thread, which is the opposite of what some tutorials assume. This is called out explicitly here because getting it backwards is the #1 cause of "works on Windows, crashes on Mac."

10. Phased delivery roadmap
Phase 0 — Scaffolding (0.5–1 day) CMake project builds an empty GLFW/GLAD window on Mac + Linux; CI-style local script to run unit tests.
Phase 1 — Math & frames core (2–3 days) Vec3/Mat3/Mat4, Quaternion (with the SOW's exact DCM↔quaternion formulas), Euler, ReferenceFrame/FrameTransformer. Unit tests reproduce the SOW's symbolic matrices numerically.
Phase 2 — Dynamics engine (3–4 days) RigidBody, TwoBodyGravity, RK4Integrator. Validate against a known circular-orbit analytic solution (period, no attitude coupling) before adding torques.
Phase 3 — Disturbances (1–2 days) IDisturbanceModel implementations (drag, gravity-gradient, J2). Verify energy/momentum behavior with disturbances toggled on/off. No controller work in this phase.
Phase 4 — Contact/validation model (1–2 days) ContactSpringModel; reproduce the two Figure-7 scenarios (high/low m_dyn) and confirm force/velocity curves qualitatively match the SOW's expected plots.
Phase 5 — OpenGL renderer (3–4 days) GLContext (Mac-safe context hints), Shader, Mesh/MeshFactory, SceneObject, Camera. Render two colored boxes + axis triads orbiting, driven by dummy/static data first, then live SimState.

Phase 7 — Threading & integration (2 days) Split physics onto its own thread with lock-free snapshot handoff; confirm no GL calls happen off the main thread; stress-test with fast-forwarded physics (many steps/frame) vs slow render.
Phase 8 — Logging, polish, docs (1–2 days) DataLogger CSV export; README with build instructions for macOS/Linux/Windows; Doxygen-style comments on every public class/method (matches SOW's "documentation in full, with a list of variable/function descriptions").
(Total: roughly 3–4 weeks for one engineer at a careful, testable pace.)

11. Testing & verification strategy
Unit tests for every math/frame function against the SOW's explicit closed-form equations (not just internal self-consistency).
Analytic sanity checks: free 2-body orbit conserves specific energy & angular momentum to numerical tolerance over N orbits.
Regression fixtures: fixed initial conditions + fixed dt → bit-for-bit reproducible state history (catches accidental nondeterminism from threading).
Validation scenario (§5 above): the software analog of SOW Figure 7, run automatically as an integration test that asserts contact-force peak and final relative velocity land within expected bounds for both mass cases.
Cross-platform smoke test: build + run headless-render check on macOS (Apple Silicon & Intel via Rosetta if needed) and Linux, confirming identical physics output (renderer output need not be pixel-identical, just non-crashing) since physics and rendering are decoupled.

12. Decisions resolved
Square geometry — resolved: full box (cube-like), not a thin plate. A flat quad has zero thickness, so it shrinks to an invisible sliver when rotated edge-on to the camera, losing all sense of orientation at certain angles. MeshFactory::MakeSquareBox(sideLen, depth) is used for both Chaser and Target with depth set close to sideLen — a proper box, not a thin extruded plate — so it always shows a clearly readable face and reads correctly as a 3D object from any angle, not just as a depth-cue trick.
Timing verification — resolved. A dedicated TimingLogger (§6.7) measures real wall-clock duration per physics step via std::chrono::steady_clock, writes it to timing_diagnostics.csv, and computes a summary (mean/stddev/min/max/% within tolerance) so the 2 ms target rate is verified with data rather than assumed. Default kDynamicsEngineDt updated to 2 ms.
Rendering scale — resolved: zoomed-in relative-motion view. Main viewport camera tracks the Chaser/Target midpoint at object scale (§6.3); a small ECI-scale inset shows Earth and the pair's position along the orbit. True ECI scale is not used for the main view — it would render both boxes as invisible sub-pixel dots.
Video export — deferred, not in v1. The ENABLE_VIDEO_EXPORT CMake flag (§9) documents the intended design (FFmpeg piping of framebuffer reads) as a stretch goal only; nothing in the core build depends on it, and it will not be implemented in this phase.
